# 裁剪规则

## 删除对象

| 类型                 | 例子                                                                                         | 存量后端实测                              |
| -------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 装饰横幅与分割线     | `// ========== 用户模块 ==========`、`/* ***** */`、`<!-- ===== -->`                   | 127 处，真实存在                          |
| 注释掉的死代码       | `// private String oldField;`、`//  if (CollUtil.isEmpty(x)) {`                          | 106 处，集中在 `HardwareViewController` |
| emoji 与无义装饰     | `// TODO 🚀`、`// ★ 重要`、`// ➜ 下一步`                                             | 未检出                                    |
| 翻译式注释           | 方法 `setName()` 上写 `// 设置名称`                                                      | 需人工判断                                |
| 复述代码             | `// 循环遍历`、`// 判空`、`// 返回结果`                                                | 需人工判断                                |
| 调用关系与调用链     | `// 由审核服务在通过或驳回时写入`、`// 被 xxController 调用`、`// 下游 xxHandler 消费` | 需人工判断                                |
| 变更履历             | `// modify by lisi`、`// 2023-05-11 张三 新增`                                           | 后端 0 处                                 |
| 流程标语             | `// 第一步：校验`、`// 开始处理`                                                         | 需人工判断                                |
| 简单方法上的 Javadoc | 三行 Javadoc 说明一个 `getId()`                                                            | 需人工判断                                |
| 无信息量的占位       | `/** 构造方法 */`、`// 无`                                                               | 需人工判断                                |
| 写成一段的长注释     | 三行以上的类头 Javadoc 补充、几十字的括号注、成段的模板注释                                  | 见下节「压缩长注释」                      |

「存量后端实测」列是 2026-09-23 对一个存量后端项目（990 个 Java 文件规模）跑正则得到的数量，只用来判断**哪些模式值得先扫**，不代表新项目。新项目规模不同，数字会变，先扫这两类能命中的，再靠人工判断其余的——不要指望正则捞出全部。日期开头的变更履历注释（`// 20xx-xx-xx`）实测 0 处，不要为一类不存在的模式写复杂正则。

**横幅注释先剥装饰，别整行删。** 后端现有 127 行这种写法，其中多数横幅本身带着下一段代码在做什么：

```java
// ===================== 批量一次性查全时段告警，不再循环单条count =====================
```

正确做法是只去掉 `=====` 装饰，留下句子：

```java
// 批量一次性查全时段告警，不再循环单条 count
```

只有文字本身也是空话时才整行删，例如 `// ============ 工具方法 ============`。

## 保留对象

| 类型             | 例子                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| 业务规则与口径   | `// 区县级账号无下级区域时回退统计本级`                                                         |
| 补偿性处理与坑   | `// 虚谷库不支持按聚合表达式排序，须用 SELECT 别名`（团队主力数据库的已知限制，写清库名与原因） |
| 单位、精度与量纲 | `// 金额单位：万元`                                                                             |
| 功能性指令       | `//noinspection`、`eslint-disable-next-line`、`@SuppressWarnings`、`@SuppressFBWarnings`  |
| 待办标记         | `TODO`、`FIXME`（去掉装饰，写清做什么）                                                       |
| 接口契约说明     | `@ApiModelProperty`、`@ApiOperation`、`@Api`                                                |

保留只决定删不删，不决定长短：留下来的注释照样按篇幅标准压短才收工。

上表里没有"数据来源""谁写入了这个值"这一类。注释写的是**本段代码自身**：它在做什么、为什么这么做、口径与单位是什么、踩过哪个坑。谁在什么时机调用它、它写完谁会消费，属于调用关系，不进注释。

## 压缩长注释

**篇幅按 `chinese-writing` 插件的篇幅标准执行。** 本插件只执行，不再另立标准。代码内部的注释同一条：行内 `//`、`/* */`、Mapper XML 的 `--`、模板 `<!-- -->`。看注释不是读小说，一段话的注释与复述代码的注释一样是噪音。

**怎么压：** 删掉推导过程、举例与语气词，留下结论与关键字（库名、字段、后果、单位）。原来两行的合成一行，原来一整段的压成一句。承载业务口径的长注释也照压——留不等于写长。

**三种不受篇幅上限限制：** 类头 Javadoc 与文件头注释块（格式见 `header-comment` 技能，整块不动，补充说明压到一句）、功能性指令（`eslint-disable`、`//noinspection`、`@SuppressWarnings` 按语法原样）、注解值（`@ApiModelProperty`、`@ApiOperation` 的 value 与 notes 属接口文档，不算注释，但同样不该摊成一段）。

**压不下去又丢不得的：** 不删，列入报告让用户定，由用户决定是挪进命名还是写进文档。

```java
// 改前
/**
 * 登录人下辖的下级区域（省取市、市取区县）；区县无下级区域时返回本级，保证至少带出自身。
 * 登录人无区域或区域码非法时返回空列表，此时不做区域补齐
 */

// 改后
/**
 * 登录人下辖的下级区域（省取市、市取区县），区县无下级时返回本级，无区域或区域码非法时返回空列表
 */
```

## 判断标准

两条，先问留不留，再问长不长：

1. **删掉这行，后来人会误改或者看不懂吗？**
   - 会，留。
   - 不会，只是"看着像注释"，删。
   - 拿不准，留。删错了要重建，留多了顶多占一行。清理的收益不值得冒丢信息的风险。
2. **留下的话，一行写得完吗？**
   - 写得完，就这样。
   - 写不完，压到一句；压了还超篇幅上限就列入报告让用户定。

这两条同时是 `comment-trimmer` 子代理的判据，别在别处再写一份。

## 绝对不做

- 不改代码逻辑。裁剪只碰注释与空行。
- 不动字符串字面量、注解值、SQL 字符串里的任何字符——那里的 `→`、`★` 是数据不是样式。
- 注释里遇到箭头不整行删句子，改写成文字；拿不准就保留并列入报告。
- 不把长注释整段删掉——能压就压，只删装饰与废话。压到篇幅上限仍丢信息的，报给用户，不自行取舍。
- 不新写超过篇幅上限的注释，也不在注释里补背景故事或举例。
- 不动本次没有编辑的文件。顺手裁剪的入口是自己正在改的文件，不是"路过觉得乱"。
- 不把字段上的 `@ApiModelProperty` 当注释删掉，也不把它改成 Javadoc。它是接口文档，不是装饰。
- 不删 eslint 指令、`@SuppressWarnings`、`//noinspection`。
- 不删 `TODO`、`FIXME`，只去装饰。
- 不动 `node_modules/`、`target/`、`dist/`、`build/` 下的任何东西。
